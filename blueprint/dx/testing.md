# Testing helpers

Imported from `@lovrozagar/flare/testing`. These are for the app's tests. They are not a second server config. Framework e2e apps, and which runtime boots them, are B70. This module does not boot `packages/core/tests/e2e/apps`.

## createTestServer

```ts
createTestServer(router, options?): { fetch(input: RequestInfo | URL, init?: RequestInit): Promise<Response> }
```

`router` is required: anything but the object `createRouter` returns throws at the call, naming `router`, as `createServer` and `createClient` do (`testing/harness.test.ts` `router required`, BUGS.md 477). `options` is `{ serverContext }` and nothing else: required when `FlareRegister` declares `serverContext`, and optional otherwise, because without it the app's loaders cannot call `serverCtx()` (revised 2026-10-13, BUGS.md B25). Any other key does not type-check and throws: an own enumerable string key, as `Object.keys` lists it, and a third argument, `undefined` included. An inherited key is not read, and a symbol key is ignored. The helper calls `createServer({ router, serverContext })`. A test that needs `site`, `store`, `authenticate`, or `locale` constructs `createServer` itself and calls `fetch`. The helper does not listen on a port (`testing/harness.test.ts` `boots`). A relative input resolves against `http://localhost`, so a protocol-relative one, `//other.example/`, is a request to that host, which the server answers as any other.

## flarePage

```ts
flarePage(page): { load, consoleErrors, state }
```

`page` is a Playwright `Page`. The methods are:

| method | args | outcome | pitfall | test |
| --- | --- | --- | --- | --- |
| `load` | `path = "/"` | `goto` that path, returning once its response commits rather than at the load event, and resolves when `<html data-flare-hydrated>` is set, so a resource that holds the load event (a pixel, a long poll) does not hold it (BUGS.md 472). It listens on two channels, so a reply Playwright's Firefox driver loses cannot hang it (BUGS.md 107): a binding the page calls when the attribute appears, and a locator `waitFor` query with a 5 s driver timeout, sent again when that ends or when its own 6 s timer does. The query returns no element handle, so one still in flight when the case ends leaves nothing to bind. Each query sent again logs one `console.warn`, and only one that is sent (BUGS.md 474). A page that has not hydrated 25 s after the call, its `goto` included, throws `The page never hydrated` (BUGS.md 473): the `goto` gets what the deadline leaves as its timeout, so a document that never answers fails the same way at 25 s. When the page logged errors since that `load` began, the message ends with them, `The page logged: …`: a mismatch that stops the boot is told by the load that fails (BUGS.md 476) | it does not wait for a deferred `c` frame. A `stream` defer is still a placeholder here. It adds one binding, named `__flare_hydrated_` plus 32 random hex digits, and one init script to the page, once per page: a second `load` reuses them | `testing/playwright.test.ts` `hydrated`, `lost reply`, `reissue`, `never hydrated`, `deadline from the call`, `never hydrated logs`, `binding once`, `reissue warns`, `page script`; `tests/integration/flare-page.test.ts` `helper on a real page`, `held load and revalidation`; e2e `docs-smoke.test.ts` `never hydrated`, which runs the same wait as `loadHydrated` with a 3 s deadline and 1 s slices |
| `consoleErrors` | none | every console error and page error the engine reported since the helper was created, a hydration mismatch Solid logs included | there is no allowlist. A test that expects a message asserts it. It holds what the engine logs, nothing more: a mismatch Solid hydrates over without a word (a tag or text the client renders differently) is not in it, and the list differs by engine (a 404 subresource logs in Chromium and WebKit, not in Firefox; Firefox's text drops an Error argument's message) | `playwright.test.ts` `console all`; `tests/integration/flare-page.test.ts` `helper on a real page` |
| `state` | none | the document's `self.flare` as it was when the page hydrated, which `load` keeps, so a later `invalidate()` or cookie-setting server function, which empties `self.flare` to `call`, does not take it (BUGS.md 475). Without a `load`, `self.flare` as it is now. Each match's `params`, `search`, `data`, and `preloader` are decoded from the wire as the client reads them (B145). `queries` is returned as the document carries it, its data still wire values | the v0 shape `{ p, r, c }` is not what this checks. The fields are `build`, `nonce`, `matches`, and `queries`; the document's other fields (`at`, `head`, `fill`, `search`) are left out. A match is `{ id, params, search, data, preloader, head, error }` (B83). It is the document's state: after a client navigation the matches are still the first page's. A `self.flare` already emptied, with no `load` to keep it, throws naming the revalidation | `playwright.test.ts` `state`, `state kept`; `tests/integration/flare-page.test.ts` `helper on a real page`, `held load and revalidation`; e2e `docs-features.test.ts` `page state` |

These v0 methods do not exist: `wasClientNavigation`, `setNavigationMarker`, `navigateNdjson`, `assertFlareStateValid`. Client navigation is asserted by the URL and the DOM, which the e2e already does.

## The framework's e2e grid

For contributors to Flare itself, not an app's tests. `bun run test:e2e` runs the 18 projects of B70 against the apps under `packages/core/tests/e2e/apps`, and the browser floor's `node-prod-floor` (B123): the production docs app in Chromium with every API newer than Chrome 111, Firefox 114, and Safari 16.4 deleted before the page runs (`tests/e2e/floor.ts`), on the specs that drive the client. `tests/structure/browser-floor.test.ts` checks every client-reachable source's browser APIs against `@mdn/browser-compat-data` at that floor. `bun run verify` (managed by `~/Development/standards`) runs fmt:check, lint, typecheck, test, test:bun, check-tree, and test:e2e in that order, stops at the first failure with its exit code, refuses a dirty tree, and when all pass stamps HEAD at `standards-verified/<sha>` in the repository's common git dir, which every worktree shares and nothing commits. That order, the refusal, the stamp, and pre-push's check are `~/Development/standards`'s, tested there (`test/verify.test.ts`, `test/pre-push.test.ts`). `bun run verify:safari` runs the client's core flows in real Safari on a Mac through its safaridriver and fails, never skips, when the Mac or the driver is unreachable (`scripts/verify-safari.test.ts`). Its flows include plan 21's client fixes: a blocker's own confirm on a link and on leaving the document (Safari under WebDriver shows no `beforeunload` prompt, so the flow dispatches the event, which asks the same confirm; probed 2026-10-22, Safari 26.6.1), Link and `navigate` under the basepath app's `/app` with their data request there too, focus on the heading and the announcement after a keyboard navigation, and the search overlay's focus trap and Escape. Blocked storage (plan 21 3.6) has no Safari flow: real blocked storage needs the user's own Safari settings or an opaque-origin iframe, whose module scripts and the docs app's CSP keep the app from booting at all, and the defect lives in engine-independent code once `sessionStorage` throws, so `tests/integration/client.test.ts` `storage blocked` in WebKit is its proof. `setLocale` has no Safari flow either: it builds its URL through the same `resolveTarget` the basePath flow exercises, and `tests/integration/basepath-client.test.ts` covers it in every engine. One run at a time drives that Safari: a run takes a lock on the Mac first and fails at once, naming the holder, while another holds it (`scripts/safari-lock.test.ts`). lefthook's pre-push refuses a push while any commit it sends has no stamp. The browsers come from the pinned Playwright image (B97): `scripts/browser-server.ts` answers `FLARE_BROWSER_WS` when set, an empty value included, for every engine, else the image's run-servers when a Docker daemon answers the shell, else Playwright's installed engines. Firefox and WebKit run in `flare-browsers` on the host network. Chromium runs in `flare-chromium` on Docker's default bridge, so another process's interface change, which fails every load Chromium has in flight with `ERR_NETWORK_CHANGED` when it shares that namespace, never reaches it (BUGS.md 484); Firefox and WebKit do not react to one. Set where a Docker daemon answers, `FLARE_BROWSER_WS` takes Chromium out of that isolation too, so the run says so once a process, naming `ERR_NETWORK_CHANGED` and that unsetting it uses the pinned containers (`scripts/browser-server.test.ts` `endpoint env costs isolation`, BUGS.md 484.8). It reaches the test servers on the host's `127.0.0.1` through `scripts/loopback-proxy.ts`, a proxy in the host-network container on a Unix socket that forwards to loopback ports 1024 and up only, so every origin stays `http://127.0.0.1:<port>` (`scripts/loopback-proxy.test.ts`, `tests/integration/network-churn.test.ts`). The machine's pruner may remove the containers and their volume when idle; each run makes what is missing. A user outside the `docker` group adds it once (`sudo usermod -aG docker "$USER"`, then a new login) or sets `FLARE_BROWSER_WS`. One project is `bun run test:e2e -- --project <name>`; a run that names its projects runs the deep specs on each of them (`scripts/browser-server.test.ts`, `tests/structure/grid.test.ts`).

Playwright's `request` fixture reuses idle keep-alive sockets across cases, so against workerd (5 s idle close) or Node (6 s) a request can land on a socket the server is closing and fail with ECONNRESET. The specs call the harness's `http` client (`tests/e2e/http.ts`) instead, which opens a fresh connection per call (BUGS.md 125).

## The framework's performance budgets

For contributors to Flare itself. Every budget is a measured value with room, and growth past one is a decision made in the commit that crosses it: the raise goes to the measured value, and its message carries the breakdown of what grew (`breakdown.ts` for a bundle, per chunk and module for the docs app). An improvement lowers the budget. Every gate budget is flip-proven: the regression it guards was planted, the check went red, then green.

- `tests/size/budget.json` holds each public export's minified gzip size, checked by `tests/size/size.test.ts` in `test`.
- `tests/perf/ssr-ratio.test.ts`, in `test` on Node and Bun, holds a Flare document's server cost to plain Solid's stream of the same tree as a ratio: the 200-row page, a 1000-row page, and the navigation data request.
- `tests/e2e/docs-perf.test.ts`, in `test:e2e` on the node-prod build in Chromium, the engine with the Long Tasks, Layout Instability, and CDP heap APIs: the docs app's document, state, NDJSON, and JavaScript bytes; the longest task; a streaming shell that sends its first bytes before a 500 ms deferred value; CLS under 0.01; under 100 requests and no URL fetched twice through idle (`tests/perf/rules.ts`); navigation that does not slow across rounds; heap and live DOM nodes that do not grow across round trips (the check that catches BUGS.md 246's `<Image>` leak); hydration time; and a production document with no dev path, Server-Timing, classic entry script, or render-blocking stylesheet.
- `.github/workflows/nightly.yml` runs what is too slow or too noisy for the gate: `packages/core/bench`'s vitest benches against the previous night's on the same runner, failing past 2x (`tests/perf/bench-compare.ts`); the v0.9.23 baseline on the same page (`tests/perf/baseline.ts --check` against `baseline.json`, the table in `tests/perf/BASELINE.md`); and docs-perf's long form (`FLARE_PERF_LONG=1`). A failing check opens one issue, a repeat comments on it, and the next green night closes it.

## The framework's black-box suites

For contributors to Flare itself. Plan 21 17.1's three suites ask the docs app's production build what any client could, each with a gate form in `test:e2e` and a long form the nightly runs (`FLARE_BLACKBOX_LONG=1`). Randomness is seeded (`tests/black-box/seeded.ts`): the gate runs a fixed seed, the long form the night's UTC date, and a failure prints the seed and the command that replays it.

- `tests/e2e/docs-hostile.test.ts` sends the hostile corpus (`tests/black-box/hostile-corpus.ts`) raw to Node, Bun, and workerd: each request gets the status and content-type class the corpus names, no answer shows a stack trace, a machine path, the probe unescaped, a smuggled header, or a production Server-Timing, and the server still answers after each. A runtime's own answer needs a BUGS row (487). The long form sends 2000 seeded mutations per runtime against the same invariants, any 5xx failing but those workerd answers itself before the worker runs (`tests/black-box/fuzz.ts` `WORKERD_OWN`).
- `tests/e2e/docs-parity.test.ts` asks Node, Bun, and workerd the same requests, the runtime-independent corpus among them, and compares status, the headers an app or a cache acts on, and the masked body (seroval's helpers, whose source text follows each runtime's copy, are masked). The long form adds every docs page and the seeded fuzz requests each runtime's HTTP parser hands to the app alike.
- `tests/e2e/docs-chaos.test.ts` drives seeded clicks, Back, Forward, and reloads, and after each step needs the page hydrated, its slot holding text, and a visible page: the share of the viewport painted apart from its background above a floor (`tests/black-box/painted.ts`), taken again a second after a blank first screenshot, since under load the first can come before the new page's first paint. Chromium also counts live DOM nodes and event listeners, which a leak grows. The gate runs 40 steps on four projects; the long form 400 on every production project.
